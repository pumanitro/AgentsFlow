Six ways Peers Flow could tell you a routine needs you

Routines run on their own while you work. Most of the time they just finish, but sometimes the agent needs you: a file to look at, a few questions to answer, a job only you can do by hand. Today Peers Flow has no way to say so. These six designs each solve that on the same real example, so you can compare them side by side and pick one.

How to read the numbers

Clicks to finish

How many clicks it takes from the moment the notice appears until it is gone: open the PDF, answer four questions, tick the to-do, send, dismiss. Typing the one written answer is not counted, only the click into the box.

Screen space when idle

How many pixels the design takes up on a quiet day, when nothing is waiting. Zero means it only appears when there is something to show.

Interruption

How hard the design pulls you away from what you are doing, from 1 (a quiet number) to 5 (takes over the screen). Too low and you miss it; too high and it gets annoying.

What I would pick

01 Bell + drawer as the base, with two ideas taken from the others.

Why the bell and drawer:

  • It is on every screen, because the header is. Home, Routines and inside a chat all share the same top bar, so the count is never out of sight.
  • It never pushes your work around. The drawer slides over the screen and slides away; nothing jumps, nothing shrinks, and on a quiet day it takes no space at all.
  • It grows from one notice to twenty. A drawer is a list, so a busy morning just means a longer list, not a cluttered screen.

The two borrowed ideas: from 04, the drawer opens by itself only for things that need you (the light notices just flash). From 06, pressing “Send answers” posts them into the routine's own chat, so the agent continues and the conversation keeps the full story.

Runner-up: 03 Needs-you tab + banner. Better if you want a place to work through several items in a row, with room for the PDF, the questions and the routine's history side by side, rather than just being told. It costs the most to build and its strip pushes the screen down until you deal with it.

How it would be built (for the engineer)

This part is the same for all six designs; each design page only adds what differs (where it sits on screen). Nothing here is written yet.

In plain words

  1. The routine's chat calls a new notify tool on the existing peersflow server, with a title, a level, files, questions and to-dos.
  2. The tool goes over the existing bridge socket to the app, which works out which routine run it belongs to and stores it in notifications.json.
  3. The app pushes it to the window, so every screen updates at once; for “something went wrong” and “needs you” it also shows a macOS banner whose click brings the window forward.
  4. You open the file, answer, tick the to-do. “Send answers” writes them into the source chat as a message; Dismiss is refused until everything is done.
  5. Routines that finish or fail on their own raise “finished” / “did not finish” notices automatically, unless the chat already raised a “needs you”.

The data shape

// shared/notifications.ts  (PROPOSED — not written in this run)
export type NotificationLevel = 'info' | 'warn' | 'action';
export interface NotificationQuestion { id: string; text: string; kind: 'yesno' | 'text' | 'choice'; choices?: string[]; hint?: string; answer?: string; answeredAt?: string }
export interface NotificationTodo { id: string; text: string; done: boolean; doneAt?: string }
export interface NotificationFile { path: string; label?: string }        // absolute; opened through the existing open_file route (PDF → system viewer, else in-app)
export interface NotificationSource { kind: 'routine' | 'chat' | 'app'; routineId?: string; runId?: string; conversationId?: string; directoryId?: string }
export interface Notification { id: string; level: NotificationLevel; title: string; body?: string; source: NotificationSource; createdAt: string; readAt?: string; dismissedAt?: string; files?: NotificationFile[]; questions?: NotificationQuestion[]; todos?: NotificationTodo[]; answersSentAt?: string }
export interface NotificationsSnapshot { notifications: Notification[]; now: string }
export const NOTIFICATIONS_IPC = { list: 'notifications:list', answer: 'notifications:answer', setTodo: 'notifications:setTodo', sendAnswers: 'notifications:sendAnswers', dismiss: 'notifications:dismiss', updated: 'notifications:updated' } as const;
export const canDismiss = (n: Notification) => n.level !== 'action' || ((n.questions ?? []).every(q => q.answer !== undefined) && (n.todos ?? []).every(t => t.done));

The path through the code

  • Routine chat calls notify → agentsflow-mcp-server.ts toolNotify → bridgeRequest({type:'notify', rootConversationId, …}, 20_000).
  • delegation-bridge.ts: new NotifyRequest + handlers.onNotify → main.ts handleNotify (resolves the source chat → directory → routine run via run.conversationId).
  • New electron/notifications-store.ts: <userData>/notifications.json, same shape as routines-store.ts (FILE_VERSION, 250 ms debounced save, sanitize on load, 180-day retention).
  • mainWindow.webContents.send('notifications:updated', snapshot); for warn/action also an Electron new Notification({title, body}) whose click focuses the window.
  • preload.ts adds listNotifications, answerNotificationQuestion, setNotificationTodo, sendNotificationAnswers, dismissNotification, onNotificationsUpdated → renderer/lib/use-notifications.ts (mirrors use-routines.ts) → the chosen design's components.
  • Auto-raised notices: routine-scheduler.ts endRun() raises info “Routine X finished” on success and warn “Routine X failed: …” on failure, unless that run's chat already raised an action.
  • Answers back: sendNotificationAnswers(id) composes “Answers to your questions: 1) … 4) …; to-do done”, posts it into the source chat (Claude: the attached PTY, or claude --resume <sessionId> -p when idle; Codex: codexSend) and stamps answersSentAt.
  • Dismiss: main refuses unless canDismiss(); the UI disables the button and explains. readAt is set when the notification is first shown open. An open action keeps the routine run at attention; dismissal lets it settle to success.

One difference between the pages and this sketch

All six design pages keep Dismiss locked until the answers have also been sent (they check answersSentAt as well), which is one step stricter than canDismiss() above. Either rule works; if the stricter one is kept, add && !!n.answersSentAt for action notices in canDismiss so the main process and the UI agree.
